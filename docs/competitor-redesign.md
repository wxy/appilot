# 竞品雷达 / 竞品跟踪 设计细化（v2：以竞品 App 为中心）

> 状态：设计稿（未实现）。目标读者：本产品负责人 + 实现同学。
> 关联现状代码：`src/renderer/components/keywords/CompetitorPanel.tsx`、
> `src/main/handlers/competitors.ts`、竞品排名快照（按 竞品×关键词×商店×平台）。

---

## 1. 现状与问题

### 1.1 现在的数据模型
- **竞品实体**：`competitor`（name、按平台的 trackIds、notes、addedAt）。
- **关键词关联**：`linkedKeywords: {keyword, language}[]`——添加竞品时把“搜索框里正在搜的词”关联到该竞品上（每次添加通常只关联一个词）。
- **竞品排名快照**：按 `(竞品, 关键词, 商店, 平台)` 记录 `rank + checkedAt`（每日/刷新时采集）。
- 自己的排名：product.rankSnapshots（`keyword × language × storefront`）。

### 1.2 现在的界面
「竞品雷达」页 = ①搜索候选卡片（App 商店搜索结果，可一键添加）+ ②「竞品跟踪」表：
- 顶部是一排**关联关键词 chips**（来自所有竞品 linkedKeywords 的并集，且按当前语言过滤）；
- 选中某个关键词后，表格：行 = **我** + 关联了该词的竞品；列 = 该语言的商店；
- 每格显示名次（颜色分级），无「未上榜」。

### 1.3 核心问题
> 一个 App 可能在**多个关键词**上与我们竞争，但当前所有视图都被关键词“切片”：
1. **竞品实体被切片**：要看某竞品在哪些词上压我们，必须手动在多个关键词 chips 间来回切换、脑内拼图；
2. **缺少“竞争面”聚合视图**：无法回答“哪些 App 是我们的头号对手”“这个竞品总共在几个词上赢我们”；
3. **关联是人工逐词成本**：添加竞品只绑一个词；后续竞品在我们其他词上出现时不会被发现（没有自动聚合机制）；
4. **无强度/趋势指标**：没有“竞争指数”“新出现竞品”“反超”这类可直接决策的信号。

## 2. 设计目标与视角翻转

| | 现状（关键词为中心） | 目标（竞品 App 为中心） |
|---|---|---|
| 主角 | 关键词（chips 切换） | 竞品 App 实体 |
| 一个竞品多个词 | 需人工切换拼图 | 档案内一屏可见（竞争面） |
| 添加成本 | 每词手动关联 | 一次添加 + 批量/自动聚合重叠词 |
| 决策信号 | 单词名次 | 竞争指数 / 事件（新出现、反超） |

保留关键词维度的价值（“这个词上谁在跟我打”是合法问题），但把它降级为
**竞品档案内部的筛选维度**，而不是一级导航。

## 3. 数据模型（后端演进）

### 3.1 竞品档案 = 实体 + 竞争面
```
CompetitorProfile {
  // 实体（既有字段保留）
  id, name,
  trackIds: { ios?: id, macos?: id },        // 同品牌多平台
  githubUrl?, notes?, addedAt,

  // 竞争面（由 linkedKeywords 升级/聚合而来，保留兼容）
  faces: [{
    language: 'en' | 'ko' | …,
    keyword: '…',
    // 该词上的采集证据
    bestRank?: number,          // 该竞品在此词上的历史最好名次（按平台）
    latestRank?: number,        // 最新名次
    firstSeenAt?, lastCheckedAt?,
    // 与我方对比（可实时由双方快照算，也可物化）
    overlap: 'both' | 'selfOnly' | 'competitorOnly',  // 当前交集状态
    leadDelta?: number,          // 它 - 我（负 = 它领先，正 = 我领先）
  }],
}
```

### 3.2 “竞争面”的三种填充方式（按成本递增）
1. **手动关联**（保留现状）：添加竞品时默认绑当前词；
2. **批量补关联**：添加竞品后可一次勾选我方多个关键词关联（UI 提供）；
3. **自动聚合（推荐，见 §6 扫描策略）**：定期扫描我方关键词的商店搜索结果，
   发现“该 App 在我方某个词上在榜”即写入 face（增量，幂等）。

### 3.3 数据存储建议
- 新增结构化表或 blob 域：`competitor_faces`（competitorId, platform, language,
  keyword, bestRank, latestRank, firstSeenAt, lastCheckedAt, …），主键
  `(competitorId, platform, language, keyword)`；
- 现有 competitor 列表与快照表不动（兼容），face 聚合在读取时由
  “列表 × faces × 我方快照”组装；
- 所有“对比我 vs 它”的指标在**读取时实时计算**（数据量小，避免双写不一致）。

## 4. 指标定义

### 4.1 竞争指数（一个竞品的总威胁度）
```
competitionIndex(C) = Σ_{face f of C}  weight(kw_f) × threat(f)

weight(kw)  // 我方该词的重要度，建议用我方自己名次段（不是竞品名次）：
  myRank ≤ 50            → 4（主力词：直接争流量）
  myRank ≤ 200           → 2
  我方未上榜但词在采集    → 1（对方占领的潜在流量）

threat(f)  // 该词上竞品相对我们的威胁：
  竞品领先我（delta<0）    → 1.5
  双方都在榜且我领先        → 0.6
  竞品在榜我未在榜          → 1.0
  都未在榜（仅历史）        → 0
```
- 归一化展示：`竞争指数 = Σ / 该竞品 face 数` 或直接给 Σ，避免“词多必大”；
  建议同时展示原始 Σ 与 `压制我方词数 / 重叠词数`。

### 4.2 事件 / 信号（每日 diff，跨天比较 faces 与双方快照）
- **新出现竞品**：竞品在某个此前只有我方/无交集的词上首次上榜；
- **反超**：上一观察日我领先（或它在 200 外），今天它 ≤ 我；
- **被甩开**：反向（我反超它）；
- **失守**：我们原本在榜的词掉出，竞品仍在。
- 呈现为竞品行上的徽标 / 总览顶部的“竞争动态”摘要条。

## 5. 界面结构（v2）

### 5.1 页面布局：一个面板三段（或两个 Tab）
```
竞品雷达
┌──────────────────────────────────────────────────────────┐
│ [搜索候选（App Store 搜索，现状保留，交互增强）]               │
├──────────────────────────────────────────────────────────┤
│ 竞品总览（默认视图，按竞争指数排序）                          │
│  行 = 一个竞品 App                                           │
│  列 = 名称/平台 | 重叠词数 | 压制我的词数 | 竞争指数 | 动态     │
│  点击行 → 展开详情                                           │
├──────────────────────────────────────────────────────────┤
│ 竞品详情（选中某竞品后）                                    │
│  竞争面矩阵：行 = 关键词（按语言分组） 列 = 商店             │
│  每格 = 我 vs 它（例：27 / 3）· 差值为 0/负 时红底强调         │
│  顶部 chips = 该竞品的重叠关键词（选中=只看该词的商店列）      │
└──────────────────────────────────────────────────────────┘
```

### 5.2 竞品总览行（App 视角）
```
[App 图标] Competitor Name   [iOS][macOS]
  竞争面：8 词重叠 · 5 词压我 · 竞争指数 12.4 · ▲2 词新出现
  最近排名：9/1 在 en:us #34 → 点开看矩阵
```
- 排序：竞争指数 desc；
- “词内对比”不再要求先选词：直接看 App 级概览，再看详情矩阵。

### 5.3 竞品详情：竞争面矩阵（核心新视图）
- 行：`语言组（英语/韩语…）→ 该竞品在该语言下重叠的关键词`；
- 列：该语言的商店（与关键词矩阵同套 storefront 规则）；
- 格值：`我方名次 / 竞品名次`（未上榜 = `—`），背景色表示相对状态：
  - 红：竞品领先我（它<我）；绿：我领先；灰：仅一方在榜 / 未查；
- 关键词行尾附一行摘要：该词“竞品最好名次 / 最近名次”，以及我方最好名次；
- 顶部保留关键词 chips（同一竞品档案内的词），但**不再是页面级导航**，
  而只是矩阵行过滤；
- 支持按“竞品在榜我未在榜”“竞品压我”等状态过滤行。

### 5.4 添加/关联交互
- 搜索结果卡片加“已存在该竞品”提示时，不只显示“已添加”，而是
  **展开其竞争面预览**：该候选 App 与我方哪些词重叠（有数据时）；
- “添加”后默认关联当前词 + 弹“批量关联更多词”多选（可选，不打断主流程）；
- 竞品详情/总览行内提供“关联更多关键词”入口（把“重叠词”做成**显式可编辑列表**）。

### 5.5 词内对比保留入口
- 关键词矩阵页原有的“竞品跟踪”逻辑不删除：在竞品详情选中某个词时
  仍可切回“该词 × 全部竞品 × 商店”的横表（现状表），作为辅助视角。

## 6. 采集成本与自动发现策略（关键取舍）

诚实前提：**我方排名采集只查“我”**，拿不到竞品在我方词上的名次；
竞品名次必须针对 (竞品 × 词 × 商店) 单独查询。因此“自动发现重叠词”
有成本，需要限流策略：

1. **默认：按需 + 低频**
   - 候选：每 24h 对**我方在榜词**（rank ≤ 200，通常远小于全池）做一次
     “前 N 名扫描”（N≈50–60，iTunes Search API 一次返回一批），
     记录出现在结果里的 App 与其名次 → 命中既有竞品则写 face，同时发现新候选；
   - 频率先做 **1 次/天/产品**，量级：在榜词 × 商店数 × 1 次/天；
2. **手动深度扫描**：详情页“扫描该词全部前 200”按钮（用户主动触发，不限频）；
3. **不做全池扫描**：全部关键词（数百）× 全部商店全扫在 API 配额上不现实；
4. 竞品详情“最近名次”若 stale（> 48h）提供单格“立即查”刷新（现状已有刷新排名入口）。

## 7. 分期落地与验收

### P1（数据层，建议先行）
- [ ] competitor faces 存储结构 + 迁移现有 linkedKeywords 到 faces（兼容读）；
- [ ] 读取时组装：face ∪ 我方快照 → 每词对比（delta / overlap）；
- [ ] 竞争指数、事件 diff（新出现/反超/失守）计算纯函数 + 单测；
- [ ] 竞品列表接口增加聚合字段（facesCount、压制数、指数、事件），不动现有字段。

**P1 验收**：接口层能回答——“某竞品在所有词上的面、每词的 我 vs 它、
竞品列表按指数排序、今日事件列表”，全部由既有数据计算得出。

### P2（UI，App 中心视图）
- [ ] 竞品总览表（行=竞品，按指数排序，含动态徽标）；
- [ ] 竞品详情竞争面矩阵（行=词、列=商店、格=我 vs 它、状态色）；
- [ ] 总览↔详情（点击行展开）、词内对比横表保留入口；
- [ ] 空态/引导：无竞品、竞品无重叠词、数据未采集的提示。

**P2 验收**：不看代码，仅从界面回答“头号竞品是谁、它压我哪几个词、每词领先多少”。

### P3（自动发现 + 事件流）
- [ ] 在榜词前 N 名低频扫描（限流/幂等/失败重试）；
- [ ] 新候选推荐（扫描中发现的未跟踪 App → 总览“发现新竞品”列表，一键添加）；
- [ ] 事件中心/摘要条：新出现、反超、失守、被甩开。

## 8. 开放问题（需拍板）
1. **竞争指数公式**：§4.1 的权重是否合理？“词重要性”暂时只用我方名次段，
   是否要引入“词 = 我们商店文案关键词/品牌词”等人工权重？
2. **重叠词采集范围**：先只扫“我方在榜词”，还是允许用户圈定一组
   “核心词”（比如 ≤20 个）每天扫描？（后者成本可控、覆盖最值得盯的词）
3. **多平台口径**：同一竞品 iOS/macOS 分开统计（建议），竞争指数是否按平台
   分开展示（总览行内两个平台的徽标/数值）？
4. **隐私/噪音**：是否把“竞品在榜但与我排名都 >200”的词降权显示
   （防止长尾词把指数刷大）。

---

## 9. 一句话总结
把“关键词 chips + 竞品行”翻转成**“竞品档案（实体）+ 竞争面（词×商店矩阵 vs 我）”**：
总览回答“谁是我的头号对手”，详情回答“它在哪些词、哪些商店压我、领先多少”，
并用量化指数与“新出现/反超”事件把零散名次变成决策信号。
