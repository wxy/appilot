# 发布工作台信息架构整理

> 状态：已确认并实施。范围只包含发布工作台，不调整全局顶栏、项目左栏或其他项目功能页。

## 1. 现状判断

当前应用的前两层结构是清楚的：

1. 全局顶栏承载应用入口、全局状态、任务中心和设置；
2. 项目左栏选择当前项目，并在总览、副驾、发布、排名、评论、趋势之间切换。

嵌套感主要来自发布工作台内部的第三个常驻区域。它看起来像第二个左侧导航，实际同时承担四种职责：

- 工作台模式：文案计划、工作中的草案、已定稿文案；
- 对象选择：历史版本列表；
- 工作流上下文：变更摘要、固定素材；
- 状态表达：是否工作中、是否同步 ASC、语言数量和更新时间。

顶部发布流程、内部左栏和编辑器语言页签又都使用了“可切换区域”的视觉形式，导致用户需要判断每一层控制的是页面、版本、阶段还是语言。

代码状态也反映了这个问题：`viewMode`、`step`、`historyDraft`、`showChecklist` 共同决定主区内容；其中 `step` 声明了三步，实际只使用 1 和 2，而且可以从“是否已有草案”推导，不应继续作为独立导航状态。

## 2. 信息层级

发布工作台内部只保留三种层级，且采用不同的视觉形式：

| 层级 | 回答的问题 | 形式 |
|---|---|---|
| 工作台模式 | 我现在要处理当前发布、做未来计划，还是查旧文案？ | 页面标题下的横向分段切换 |
| 当前对象 | 当前是哪个平台、GitHub Release 和商店版本？ | 上下文栏与三段状态图 |
| 内容维度 | 当前文案查看或编辑哪种语言？ | 文案编辑器内部语言页签 |

发布检查、商店文案比对、恢复本地文案属于辅助任务，不占用导航层级。发布检查在状态图下方进入聚焦工作区；商店文案比对与恢复在对话框中完成。

## 3. 推荐结构

```text
全局顶栏
└─ 项目左栏：发布
   └─ 发布工作台
      ├─ 标题与上下文：项目 / 平台 / 凭据
      ├─ 模式切换：[当前发布] [文案计划] [历史文案]
      ├─ 当前发布状态：GitHub → 发布文案 → 商店版本
      └─ 主工作区（单列、占满剩余宽度）
         ├─ 状态概览：版本 / 内容状态 / 商店交付状态 / 主要操作
         ├─ 发布依据（仅待创建或编辑时出现）：变更摘要 / 固定素材
         ├─ 商店提交工作单（按需进入）
         │  └─ 语言页签
         ├─ 聚焦检查工作区：发布检查
         └─ 商店文案对话框：比对 / 恢复
```

### 3.1 模式切换

使用三个稳定入口：

- **当前发布**：根据发布目标自动呈现“待创建 / 编辑中 / 已定稿”三种内容状态。
- **文案计划**：未来发布的改进方向和素材计划。
- **历史文案**：只收纳已经被后续版本取代的文案，选择后进入全宽只读详情。

每份版本文案内部以“商店文案 / 截图文案”切换。两者只共享版本归属、产品信息和支持语言目录。截图文案使用界面语言作为固定母本语言，用户选择目标语言；截图类型不排序，标题和描述均为支持双击复制的单行字段。生成母本后仍是编辑状态，必须明确确定母本，其他语言页才开放逐一翻译。其缺失或未完成不阻塞商店文案。AI 读取项目档案和本次发布信息生成整组截图母本。

截图文案以截图类型卡片呈现。每张卡片包含图片（`appilot.image`）、标题（`appilot.title`）和描述（`appilot.description`）；母本语言选择默认图片，目标语言默认继承该图，也可单独替换或恢复继承。图片选择独立于文案确认状态，因此整批文案确定后仍可继续补齐各语言截图。

Keynote 自动化要求模板中唯一存在名为 `appilot.screenshot.v1` 的母板，并在生成的页面中提供两个可编辑文本占位符及一个可编辑媒体占位符。用户选择模板和输出文件后，Appilot 先创建不继承模板文稿 UUID 的临时副本，通过 macOS 将这个具体副本交给 Keynote，在副本中为“语言 × 截图类型”生成页面、填入文字和图片并删除副本原有页面；全部成功后才落到用户指定的新 `.key` 文件。模板原件不打开写入，也不清空。

“正在编辑”和“正式文案”不做成两个永久导航入口。系统根据数据决定当前主状态；存在下一版工作目标时，上一份正式文案仍作为基准保留，但不与工作目标竞争主区。

### 3.2 当前发布

- “当前发布”是一个生命周期容器，而不是一份固定文案。它包含两个逻辑位置：
  - **当前待办目标**：最新但尚未形成正式文案的发布，可处于待创建或编辑中；
  - **正式文案基线**：最近一次整批确定的文案，可处于准备提交、等待审核、审核中或已上架。
- 两个位置可以同时存在。例如正在编辑 v1.2.0 时，商店仍在使用或审核 v1.1.3。此时 v1.2.0 是主工作区，v1.1.3 以“正式基线”摘要显示，并提供查看或比较入口。
- 主工作状态由系统自动决定：
  1. 有待办目标且有草案 → **编辑中**；
  2. 有待办目标但无草案 → **待创建**；
  3. 没有待办目标但有正式基线 → **已定稿**；
  4. 两者都没有 → **暂无发布文案**。
- 草案整批确定后，它晋升为新的正式基线，当前待办目标随之清空。商店审核与上架只改变正式文案的交付状态，不把它移入历史。
- 保留三段状态图，因为它表达 GitHub、文案和商店之间的真实关系；压缩纵向留白，使其更像上下文状态条。
- 版本号、平台和凭据只在页头出现一次。
- “发布检查”从状态条打开其下方的全宽检查工作区；检查期间隐藏状态概览和工作单，返回后恢复原工作位置。
- “比对商店文案”和“从商店恢复”归入同一个文案差异对话框；恢复入口只在对话框中出现，并明确覆盖方向。
- 已定稿状态默认只显示状态概览。完整的多语言工作单通过“查看完整文案”进入，避免把流程、检查、商店操作和所有字段同时铺在一个长页面中。
- 进入完整文案后隐藏大块发布流程，状态概览条同时承担返回、版本状态、商店比对和发布检查入口，文案内容直接进入首屏。
- 文案版本只从 GitHub 发布 tag 或名称推断，不在文案表单中提供重复的“目标版本”输入。
- 已定稿概览中的文案版本号直接作为详情入口，并显示“点击查看文案”提示，不再增加独立的“查看完整文案”按钮。
- 按钮按动作层级统一：生成和执行使用主按钮；发布检查、商店比对、刷新等辅助动作使用统一的小号次级按钮；语言与筛选使用选择控件；删除和返回使用对应的行级或图标控件。

三种主状态的内容组织如下：

| 主状态 | 页头 | 主区 | 正式基线 |
|---|---|---|---|
| 已定稿 | `v1.1.3 · 已定稿`，另附“待提交 / 等待审核 / 审核中 / 已上架”等商店状态 | 默认显示紧凑概览；按需进入完整文案详情，允许比对商店和处理驳回意见 | 它自身就是主区，不重复显示 |
| 编辑中 | `v1.2.0 · 编辑中`，附母本与语言完成度 | 可编辑工作单和发布依据 | 紧凑显示 `基准：v1.1.3 · 已上架`，可查看或比较 |
| 待创建 | `v1.2.0 · 待创建`，附 GitHub tag 和变更数量 | 发布依据摘要与唯一主操作“创建发布文案” | 有则紧凑显示，帮助理解本次变化；无则不占位 |

状态迁移遵循以下规则：

| 事件 | 迁移 |
|---|---|
| 发现尚未覆盖的新 GitHub 发布 | 已定稿 → 待创建；旧正式文案继续作为基线 |
| 创建或生成第一份文案 | 待创建 → 编辑中 |
| 整批文案确定 | 编辑中 → 已定稿；旧正式文案进入历史 |
| 提交审核、进入审核、审核通过 | 不改变“已定稿”内容状态，只更新商店交付状态 |
| 商店驳回 | 正式快照保留并标记“已驳回”；用户发起修订后创建编辑稿，正式快照作为被驳回版本的基线 |
| 已上架后回读商店文案 | 更新正式快照的商店对齐内容与时间，不产生新的工作状态 |

### 3.3 发布依据

变更摘要和固定素材是生成文案的输入，不是导航。它们移到主列顶部的可展开区：

- 默认显示摘要：PR 数、提交数、时间范围和已选择条目数；
- 展开后可勾选变更，并查看固定素材；
- 生成完成后默认折叠，编辑文案时把空间还给工作单。

### 3.4 历史文案

- 当前正式文案不进入历史，它始终属于“当前发布”；只有被新正式版本取代后才进入历史。
- 列表和详情不再挤在 288px 左栏中；列表使用主区全宽，展示版本、当时的最终状态、语言数、更新时间和 ASC 同步状态；
- 点击版本进入同一主区的只读详情，使用明确的返回路径；
- “未完成”的旧草案属于异常或被超越的工作记录，需要单独标为“未完成”，不能冒充正式历史版本。

## 4. 状态模型建议

第一轮布局迁移保持后端和数据结构不变。随后把页面状态收敛为：

```ts
type ReleaseSurface =
  | { mode: "current" }
  | { mode: "plan" }
  | { mode: "history"; draftId?: string };

type CurrentReleaseWorkspace =
  | { phase: "official"; official: StoreSubmissionDraft }
  | { phase: "editing"; target: ReleaseInfo; draft: StoreSubmissionDraft; official?: StoreSubmissionDraft }
  | { phase: "needs-creation"; target: ReleaseInfo; official?: StoreSubmissionDraft }
  | { phase: "empty" };

type ReleaseAuxiliaryState = {
  focusedTask: "checks" | "copy-details" | null;
  dialog: "store-copy" | null;
};
```

- 删除可推导的 `step`；是否显示生成准备或工作单由当前发布和草案直接决定。
- `showChecklist` 控制状态图下方的聚焦检查工作区；打开时隐藏主工作单，避免页面同时堆叠多项任务。
- 正式文案的内容成熟度与商店交付状态分开：`batchConfirmedAt` 决定它是否已成型，ASC 状态决定它处于等待审核、审核中还是已上架。
- URL 保留 `tag`，并使用稳定的 `view=current|plan|history`、`draft=<id>`、`lang=<code>`，使版本和语言视图可恢复、可深链。

## 5. 迁移顺序

1. 新增横向模式切换，把文案计划、当前发布、历史文案从内部左栏移出；不改业务处理函数。
2. 将变更摘要和固定素材迁入主列的“发布依据”折叠区，移除常驻 288px 栏。
3. 按“已定稿 / 编辑中 / 待创建”渲染当前发布主区，并在后两者中保留正式基线摘要。
4. 将发布检查改为状态图下方的聚焦工作区，将商店比对改为对话框，保持当前版本上下文。
5. 将历史列表升级为全宽历史页，再收敛 `viewMode`、`step`、`historyDraft` 和 URL 状态。
6. 在现有 Electron 开发版中逐个验证新建、生成、翻译、定稿、提交审核、上架、检查、商店比对和历史查看。

## 6. 验收标准

- 发布页不再出现第三个常驻侧栏；应用中只有全局顶栏和项目左栏两处永久导航。
- 用户不需要选择“工作中 / 已定稿 / 新建”入口；当前发布主状态由待办目标和草案自动推导。
- 编辑或创建下一版时，仍能明确看到当前正式文案的版本与商店状态，但它不会抢占主区。
- 正式文案在等待审核、审核中和已上架期间始终留在当前发布；被新版本取代后才进入历史。
- 打开发布检查或商店比对不会丢失当前版本、语言或滚动上下文。
- 状态图只表达状态和相关动作；模式切换只负责页面模式；语言页签只负责语言。
- 1280px 宽度下工作单获得完整主列宽度，历史版本信息不被压缩成窄列表。
- 当前 URL 可恢复工作台模式、版本详情和语言选择。
