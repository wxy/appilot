# Appilot 0.4.0 设计文档 — 只读数据层增强（Apple 运营代理）

> 所属：[Appilot 设计文档集](../../README.md) | 状态：待评审 | 日期：2026-08-24
> 姊妹文件：[产品规格](./appilot-product.md) · [架构设计](./appilot-architecture.md) · [构建计划](./appilot-build-plan.md) · [Token 能力方案](../plans/2026-08-23-project-settings-and-token-capabilities.md)
> 本文档定义 0.4.0 里程碑的**只读**功能范围、架构与数据流。所有写入动作（GitHub release 写回、ASC 版本创建/填写/提交审核、评论回复）明确排除，留待 0.5.0。

## 1. 背景与目标

0.3.0 已发布，凭据体系（GitHub Token + ASC API Key 的全局默认/项目覆盖、加密存储、测试连接）已就绪。当前两个占位页（`/reviews` 评论洞察、`/trend` 长期效果）与第一梯队数据能力尚未实现。

**0.4.0 目标**：把两个占位页实装，并补齐「凭据驱动的只读数据层」——让 Appilot 从「排名 + 发布文案工具」升级为能回答以下问题的运营代理：

- 用户在商店/Issues/TestFlight 里到底在要什么（评论洞察 + 反馈收件箱）
- 发布之后发生了什么（GitHub 流量 + release 资产下载量 + ASC 下载/展示量 + 排名变化）
- 这次提交是否准备好（发布就绪体检 + 构建状态联动）
- 竞品这周在做什么（竞品发布雷达）

**已确认决策（2026-08-24）**：

| # | 决策 | 结论 |
|---|------|------|
| D1 | ASC 写入边界 | 只「读取已有版本」；不创建版本、不提交审核（决策 A） |
| D2 | GitHub 写入边界 | 只读；不更新、不发布、不创建 release（决策 A，本版本进一步收窄为完全不写入） |
| D3 | 反馈收件箱范围 | 只读聚类；回复草稿放 0.5.0（决策 A） |
| D4 | 版本写入 | 0.4.0 不引入任何写入权限，全部以只读为边界。「写入」指外部平台（GitHub/ASC）的写操作；本地草稿、跟踪集、状态等本地数据更新不受限，仍按 human-in-the-loop 由用户确认后执行 |

## 2. 范围

### 2.1 本期做（全部只读）

| # | 功能 | 数据源 | 依赖凭证 | 落点 |
|---|------|--------|----------|------|
| F1 | ASC 版本/审核状态回读 + 审核意见回读 | ASC API | ASC | 发布工作台、总览 |
| F2 | 评论洞察 | App Store 评论 RSS（免费） | 无（RSS）；ASC 评论 API 待实测 | `/reviews` 页 |
| F3 | 长期效果 | GitHub 流量 + release 资产下载量 + 排名 + ASC App Analytics（待实测） | GitHub、ASC | `/trend` 页 |
| F4 | GitHub 流量与资产下载量 | GitHub Traffic/Releases API | GitHub | `/trend`、总览 |
| F5 | 统一反馈收件箱 | GitHub Issues + F2 评论 + TestFlight 反馈（待实测） | GitHub、ASC | `/reviews`、总览 |
| F6 | 发布就绪体检 | ASC 版本/本地化 + 本地草稿 | ASC | 发布工作台 |
| F7 | 构建/TestFlight 状态联动 | ASC Builds/Beta API | ASC | 发布工作台、任务中心 |
| F8 | 竞品发布雷达 | iTunes Lookup/Search API + GitHub（可选） | GitHub（仅竞品仓库关联时） | 关键词页、总览 |

### 2.2 本期明确不做

- **所有写入动作**：GitHub release 创建/更新/转正式发布、ASC 版本创建/填写/提交审核、评论回复、issue 回复 → 0.5.0 另行设计。
- 手动回填（产品原则 D5：不能自动化的追踪能力就「缺失」）。
- 搜索量（Apple 不公开）。
- 网页爬虫/DOM 批量抓取（产品边界：不通过非官方手段大规模爬取）。
- 移动端/云端后端。

### 2.3 边界与产品原则

- **本地优先**：数据留在本机，凭据不出设备（沿用 safeStorage 加密）。
- **Human-in-the-loop**：AI 只做聚类/判断/建议；采纳动作（如主题建议关键词进跟踪集）由用户确认。
- **无手动回填**：评论/流量/竞品全部自动采集；采集不到的能力显示为「缺失」而不是表单。
- **仓库只读边界**：读取本地仓库与 GitHub Issues 属于只读，可接受；回复/发布属于写入，排除。
- **AI 用在判断层**：采集（RSS/GitHub/ASC 拉取）全部用确定性代码；AI 仅用于评论聚类、反馈主题归纳、竞品动态摘要。

## 3. 架构总览

沿用现有「engine 纯模块 + main handlers + scheduler 任务 + electron-store 持久化 + React 页面」分层，不引入新框架。

### 3.1 新增 engine 纯模块（全部可单测，mock fetch）

| 模块 | 职责 | 关键接口 |
|------|------|----------|
| `src/engine/asc-api.ts` | ASC 客户端：JWT 签发 + GET 封装 + 错误映射 | `createAscClient(creds)` → `getAppIdByBundleId()` / `listAppStoreVersions()` / `listVersionLocalizations()` / `listBuilds()` / `getReviewDetail()` / `listCustomerReviews()` / `getAnalyticsReport()`（后三个待实测） |
| `src/engine/gh-traffic.ts` | GitHub Traffic + release 资产下载量 | `fetchTrafficSnapshot(localPath, token)` / `fetchReleaseAssetDownloads(localPath, token, tag)` |
| `src/engine/review-collector.ts` | 评论 RSS 拉取与解析、增量 | `fetchCountryReviews(trackId, country)` / `fetchAllStorefrontReviews(trackId, countries, existingIds)` |
| `src/engine/feedback-inbox.ts` | 反馈归一化（issue/评论/beta）、去重、AI 聚类 | `normalizeIssue()` / `clusterFeedback(provider, context, items)` |
| `src/engine/readiness-check.ts` | 确定性发布就绪体检 | `runReadinessChecks(input)` → `ReadinessCheckItem[]` |
| `src/engine/build-status.ts` | ASC 构建状态映射 + 只读下一步建议 | `mapBuildState()` / `suggestedNextStep()` |
| `src/engine/competitor-radar.ts` | 竞品模型、候选搜索、每日快照 | `searchCompetitorCandidates()` / `fetchCompetitorSnapshot(competitor)` |
| `src/engine/ai/review-insights.ts` | AI 评论/反馈聚类提示词与结构化输出 | `generateReviewThemes(provider, context, items)` |

> `ascJwt` 与 `derToRawJwtSignature` 从 `src/main/credentials.ts` 下沉到 `asc-api.ts`（纯函数），`credentials.ts` 保留 re-export，避免破坏既有调用。

### 3.2 数据模型（electron-store 新增键）

| Key | 形状 | 说明 |
|-----|------|------|
| `reviews` | `{ [productId]: { [country]: { items: Review[], lastFetchedAt } } }` | 评论原始数据；每国保留最近 500 条 |
| `reviewThemes` | `{ [productId]: FeedbackTheme[] }` | AI 聚类结果（含证据引用与建议动作） |
| `feedback` | `{ [projectId]: { items: FeedbackItem[], themes: FeedbackTheme[], lastSyncedAt } }` | 统一反馈收件箱 |
| `trafficSnapshots` | `{ [projectId]: TrafficSnapshot[] }` | 每日流量/资产下载快照，保留 90 天 |
| `ascCache` | `{ [productId]: { appId, versions, localizations, builds, fetchedAt } }` | ASC 回读缓存 |
| `readinessChecks` | `{ [projectId]: { [draftId]: { checkedAt, items } } }` | 按发布草稿缓存的体检结果 |
| `competitors` | `{ [projectId]: Competitor[] }` | 竞品列表（手动添加 + 从排名候选一键添加） |
| `competitorSnapshots` | `{ [projectId]: { [competitorId]: CompetitorSnapshot[] } }` | 竞品每日快照，保留 90 天 |

### 3.3 调度任务（scheduler 新增类型）

| 类型 | 粒度 | 间隔 | 触发条件 |
|------|------|------|----------|
| `ops-sync` | 每项目 | 24h | 常驻：GitHub 流量 + 反馈同步 + 竞品快照 |
| `reviews-sync` | 每产品 | 24h | 常驻：按国家分批拉评论（每 tick ≤ 3 国） |
| `build-status` | 每产品 | 60min | 仅当存在 `storeStatus ∈ {prepared, copied, submitted, in_review}` 的草稿时注册，无在途发布时注销 |

> ⚠️ `reconcileRankTasks` 当前的保留过滤只允许 `github-sync` 与激活的 `rank` 任务（见 `src/main/scheduler.ts`），新增三种任务类型必须加入保留白名单，否则会被对账清掉。

### 3.4 IPC / preload 新增面

- `trend:data(projectId, productId, rangeDays)` → 组合时间线
- `traffic:sync` / `traffic:snapshots`
- `feedback:sync` / `feedback:list` / `feedback:themes`

## 4. 功能设计

### 4.1 F1 — ASC 版本/审核状态与审核意见回读

- **数据源**：ASC API（只读）。
- **流程**：`bundleId → appId → appStoreVersions → appStoreVersionLocalizations`，缓存到 `ascCache`；发布工作台展示「ASC 侧真实状态」chip（inDevelopment / awaitingReview / inReview / approved / rejected），与本地手动 `storeStatus` 并列，**不自动改写本地状态**（避免“回读即写入”的歧义）。
- **审核意见**：优先从 `appStoreReviewDetail`（待实测是否含驳回原因）回读；不可用时保留现有 `reviewFeedback` 手动粘贴作为兜底。回读内容可一键填入 `reviewFeedback` 并作为下次生成文案的上下文（复用现有流程）。
- **UI**：发布工作台草稿头部状态区 + 总览「商店状态」卡片。

### 4.2 F2 — 评论洞察（`/reviews`）

- **数据源**：App Store 评论 RSS（`itunes.apple.com/{country}/rss/customerreviews/id={trackId}/json`），免费无认证；国家集合复用 `STOREFRONTS_BY_LANGUAGE`。
- **采集**：`reviews-sync` 每日增量拉取（按评论 id 去重，每国保留最近 500 条）。
- **洞察**：`generateReviewThemes` 把「产品档案 + 评论样本」聚成主题（“用户一直要 X”），输出 `{title, evidenceCount, sampleQuotes[], suggestedKeywords[], suggestedDescriptionAngles[], sourceBreakdown}`；主题卡上的「建议动作」用户确认后进入现有跟踪关键词流或发布建议，不自动写入。
- **UI**：`/reviews` 页 = 主题卡列表（按证据数排序）+ 评论明细表（筛选：国家/评分/版本/关键词）+ 主题 ↔ 评论对照；样本不足（< 5 条）时显示「样本不足」而非伪洞察。
- **降级**：RSS 不可用时该功能标记「缺失」，不做手动回填。

### 4.3 F3 + F4 — 长期效果（`/trend`）与 GitHub 流量/资产下载

- **数据源**：GitHub Traffic API（`traffic/views`、`traffic/clones`、`traffic/popular/referrers`，14 天窗口）+ Releases API 资产 `download_count`；ASC App Analytics（`analyticsReportRequests`，待实测）；已有排名快照。
- **采集**：`ops-sync` 每日拉取一次存 `trafficSnapshots`（从接入日起每日快照，**历史不可回溯**，必须在文档中说明）。
- **UI**：`/trend` 页 = 组合时间线（release 标记 + 各关键词最佳排名 + GitHub views/clones + 资产下载量 + ASC 指标可用时），范围选择 7/14/30/90 天；数据源徽标（github/asc/免费接口）区分来源。
- **降级**：App Analytics 权限不足时 `/trend` 显示「GitHub 流量 + 排名 + release 事件」，不显示伪数据。

### 4.4 F5 — 统一反馈收件箱

- **数据源**：GitHub Issues（`GET /repos/{owner}/{repo}/issues?state=all&since=...`，含 label/state/comments 数）+ F2 评论 + TestFlight 反馈（`betaFeedback` 相关端点，待实测；不可用时收件箱只覆盖 Issues + 评论，并在 UI 标注）。
- **归一化**：`normalizeIssue` → `FeedbackItem {source, sourceId, title, body, state, url, author, createdAt}`，按 `source + sourceId` 去重。
- **洞察**：`clusterFeedback` 跨源聚类，输出主题（含来源占比与证据引用）；主题反哺「关键词建议 / 描述角度」，用户确认后进现有流程。
- **UI**：`/reviews` 页增加「全部反馈」Tab（来源筛选：评论/Issues/TestFlight）+ 主题卡；总览页显示 Top 3 主题。

### 4.5 F6 — 发布就绪体检

- **输入**：本地草稿本地化字段 + `ascCache`（ASC 本地化/版本/构建）+ 当前 git tag。
- **检查项**（纯函数，可单测）：
  - 本地化覆盖率：ASC 已有本地化语言 vs `product.supportedLanguages` 缺失项（warning）
  - 字段限制：Promotional Text ≤ 170、关键词 ≤ 100、名称/副标题 ≤ 30、描述/What's New ≤ 4000（fail）
  - 版本匹配：git tag 版本号 vs ASC 版本号（fail/unknown）
  - 构建挂载：该版本是否有可用构建（fail/unknown）
- **UI**：发布工作台「就绪体检」面板（pass/fail/warning/unknown 四态，每项含修复指引）；结果缓存到 `readinessChecks`，草稿变化后失效重查。

### 4.6 F7 — 构建/TestFlight 状态联动

- **数据源**：ASC Builds + Beta API（`builds`、`betaAppReviewSubmission`，待实测）。
- **映射**：`mapBuildState` → `processing / available / inBetaReview / rejected / unknown`；`suggestedNextStep` 输出只读提示（如“构建处理完成，可前往 App Store Connect 提交审核”）。
- **UI**：发布工作台草稿状态区显示构建 chip；任务中心「运行中/最近任务」展示 `build-status` 轮询结果。

### 4.7 F8 — 竞品发布雷达

- **竞品来源**：手动添加（名称 + trackId + 可选 GitHub 仓库）+ 从关键词候选一键添加。`searchCompetitorCandidates(term, country, entity)` 复用 iTunes Search API（返回 top 50 的 trackId/名称/评分），排在自家应用前面的可作为候选。
- **快照**：`fetchCompetitorSnapshot` = iTunes Lookup（当前版本、版本发布日期、价格、评分）+ 关联 GitHub 仓库时（stars、最近 release）；每日存入 `competitorSnapshots`。
- **洞察**：每周摘要「竞品这周发了什么版本、加了什么词、star 变化」，作为周报/归因诊断上下文（接入现有 overview brief，不新增调度）。
- **UI**：关键词页「谁排前面」候选列表（一键加为竞品）；总览页竞品雷达卡（近 7 天动态）。

## 5. 权限与安全

- **GitHub Token**：推荐 fine-grained token（Contents/Issues/Metadata 只读，限定目标仓库），避免全 `repo` scope；README 中给出申请指引。
- **ASC API Key**：0.4.0 只读，低角色 key 即可（具体角色以实测为准）；写入（0.5.0）需要 App Manager 角色，届时可能需要第二个 key——文档须提前说明。
- **凭据**：沿用 safeStorage 加密；不出设备、不进日志、不进 AI 提示词（既有原则）；新模块不新增明文持久化。
- **数据出境**：评论/Issues 原文会发送给 AI 提供方做聚类，沿用「AI 数据处理说明」的既有提示。

## 6. 验证先行任务（V0，必须在采集器编码前完成）

按 review-log §21.3 的实测风格，用真实账号验证以下数据源，结果写入本文档或评审记录，再决定最终数据源：

1. GitHub Traffic API 对真实仓库返回 views/clones/referrers；Releases API 资产含 `download_count`（需要有已发布资产）。
2. ASC 全链路：`bundleId → appId → appStoreVersions → appStoreVersionLocalizations → builds` 可读（用 GloWalk / AI Pulse 的真实 trackId）。
3. ASC App Analytics 端点（`analyticsReportRequests`）权限与配额。
4. ASC Customer Reviews 端点权限（决定评论是否从 RSS 升级）。
5. ASC TestFlight 反馈（`betaFeedback` 相关端点）是否可读（决定收件箱是否覆盖 beta）。
6. `appStoreReviewDetail` 是否含驳回原因（决定审核意见回读方案）。

## 7. 里程碑切分

- **0.4.1 数据层 + 调度**：asc-api / gh-traffic / review-collector / build-status / readiness-check / competitor-radar engine 模块 + scheduler 三种新任务 + IPC/preload + 单测。
- **0.4.2 UI**：`/reviews`、`/trend` 实装；发布工作台体检面板 + ASC/构建状态 chip；总览卡片；任务中心新任务类型；设置能力矩阵文案更新。
- **0.4.3 洞察与闭环**：feedback-inbox + review-themes AI 聚类 + 周报/归因上下文接入。

## 8. 测试策略

- engine 纯模块单测（fixture JSON + mock fetch）：评论 RSS 解析、流量解析、就绪体检、竞品快照解析、构建状态映射、主题聚类（mock AI provider）。
- scheduler：新任务类型的对账/保留白名单/注销逻辑测试（沿用 `tests/scheduler-status.test.ts` 模式）。
- 手测：两个真实产品走通 `/reviews`、`/trend`、发布工作台体检、总览卡片。
- 不引入新的测试框架或基础设施。

## 9. 风险与降级

| 风险 | 应对 |
|------|------|
| ASC 端点权限/配额不可用 | 验证先行；评论降级 RSS、`/trend` 降级 GitHub 流量 + 排名、收件箱降级 Issues + 评论 |
| GitHub Traffic 只有 14 天窗口 | 接入日起每日快照，UI/文档明示历史不可回溯 |
| 评论样本不足或 RSS 频率限制 | 每国 500 条上限；聚类显示「样本不足」；拉取失败退避重试 |
| electron-store JSON 体积增长 | 快照保留 90 天、评论每国 500 条上限、定期清理 |
| 新调度任务被既有对账清除 | 3.3 节白名单修复纳入 0.4.1 第一项任务 |

## 10. 0.5.0 预研（本版本不实现，仅记录边界）

- **GitHub 写入**：更新已有草案 release 正文 + 一键转正式发布（决策 A）；可选「按确认边界新建草案发布」显式按钮，默认关闭（决策 B 备选）。
- **ASC 写入**：读取已有版本 → 显式填入文案（决策 A）；不创建版本、不提交审核。
- **评论/issue 回复草稿**：AI 起草 + 用户确认 + API 提交（决策 A），与写入批次一起设计。
- 写入需要 App Manager 角色 key（或第二个 key）与 GitHub 写权限 token；安全边界、撤销、平台配额在 0.5.0 设计文档中展开。
